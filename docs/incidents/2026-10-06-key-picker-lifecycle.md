# Google key picker redesign (2026-10-06)

The original flow mixed key configuration with window management: Save, Load, Show window and Cancel appeared together. A pending flag could survive the useful lifetime of its native dialog. Follow-up code counted any visible window in the helper process as success, which was insufficient evidence that the user could see or operate the intended picker. The PowerShell/WinForms path also lacked a real browser owner. Earlier validation checked reported handles rather than completing the UI flow, so it missed the user-visible failure.

The replacement exposes only Save… and Open…. Save opens the modern Explorer folder picker; Open selects an existing file. Cancel is provided by the system dialog. The local service owns one operation, and repeated requests focus that same operation rather than spawning another. The last translator preference remains the user's default.

A small cached C# GUI executable now calls Windows IFileDialog with the invoking browser as owner. No PowerShell console or visible host form is created. The actual dialog is discoverable through Alt+Tab. Tracking requires the expected dialog class, visible state and nonempty bounds. Process exit, EOF, cancellation and failed heartbeats clear state. GUI startup uses explicitly encoded standard pipe streams; Console.InputEncoding was found to throw INVALID_HANDLE without a console and was removed during live testing.

The extension supplies browser bounds and page viewport geometry with Chrome zoom accounted for. The native helper centers within that browser's page area and clamps to its monitor. If the page cannot be inspected, it centers within the browser. Repeated focus restores the same window and recalculates its position. A nonempty key is accepted without guessing its syntax; Google validates it when translating.

Live Windows verification used the actual Chrome popup, typed a temporary nonsecret value, opened Save, selected an isolated folder, confirmed, and read back matching contents. It reopened setup and loaded that saved file with Open. Both operations reached done with cleared process/window state. Escape cancellation and reopening worked. A repeated authenticated request retained the same operation ID, process ID and HWND. Translation was switched off during saving/loading to avoid API requests, and test configuration was restored afterward. These checks supersede the earlier handle-only smoke test; they do not prove correctness on every Windows installation or display arrangement.

References: [Windows Common Item Dialog](https://learn.microsoft.com/en-us/windows/win32/shell/common-file-dialog), [IModalWindow.Show](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-imodalwindow-show).

Final interaction revision: the popup now has one link. Before configuration it reads "Link API key file..."; afterward the selected path itself is the link. Both open the same existing-file picker. Key-file creation was removed from the service and folder selection removed from the native helper. Only the selected path is persisted; UTF-8 file contents are trimmed at their boundaries in memory and never rewritten. Tests cover replacement, whitespace/BOM, missing/empty files preserving the previous configuration, and cancellation. The final Chrome UI was checked with the configured path: clicking it opened one native picker and Escape cancelled it.
